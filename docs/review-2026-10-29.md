# Memory, transport, and custody review and fixes — 2026-10-29

This review resumed the request to check bugs, security issues, and memory leaks.
It examined the local integration, endpoint security bridge, TCP transport,
Python record/storage code, BPNode demo, and relevant BPLib memory/decoder paths.
The three bounds findings below are fixed in source. Subsequent deployment
validation also identified the TCP timeout issue (finding 4) and a storage
startup contention/cleanup issue (finding 5), and premature custody acceptance
after a failed write/commit (finding 6). This is not an exhaustive audit of
all bundled dependencies. Git metadata was unavailable in this workspace.

## 1. P2 — Pool initialization writes the wrong number of bytes

Location: `bplib/ci/mem/src/bplib_mem.c`, `BPLib_MEM_PoolInit`.

The old `memset(init_mem, 0, sizeof(init_size))` used the size of the size variable
(eight bytes on the reviewed host), rather than the supplied buffer length.
A one-byte buffer therefore caused seven bytes beyond that range to be cleared;
a larger buffer was mostly left untouched. A probe calling the actual function
with length one and a 16-byte sentinel region observed eight zero bytes and
success. The allocator boundary was stubbed in this probe.

Fix: clear exactly `init_size` bytes. The existing nonzero-length/null checks
remain. `memory_regression` now checks a one-byte region with untouched adjacent
sentinels and complete clearing of a 32-byte region.

## 2. P2 — Blob reads can expose bytes outside stored data

Location: `bplib/ci/mem/src/bplib_mem.c`, `BPLib_MEM_CopyOutFromOffset`.

The reader used the allocation capacity (`BPLIB_MEM_BIG_BLK_DATA_SIZE`) for
skipping/copying rather than the blocks' actual `used_len`. A read extending
beyond the last stored byte could succeed and copy unused, potentially stale
pool contents into the caller's output. `BPLib_BlockReaderRead` inherits this
behavior if decoded block metadata requests such a range. No remote disclosure
through a complete deployed node was demonstrated.

Fix: locate the start using populated lengths, validate the entire requested
range before copying, and copy only populated bytes. Invalid ranges leave output
unchanged. Zero bytes at the exact end of the blob are allowed. Range validation
uses subtraction rather than potentially overflowing `Offset + length`.

`memory_regression` covers a partial final block with deterministic slack,
one-byte overreads, offsets beyond the end and `UINT64_MAX`, exact-end empty
reads, cross-block reads, insufficient output capacity, and block-reader error
propagation with zero bytes reported. Allocation failure/free coverage remains.

## 3. P1 — Excess extension blocks can write outside decoder metadata

Location: `bplib/ci/cbor/src/bplib_cbor_decode_canonical.c`,
`BPLib_CBOR_DecodeCanonical`.

The canonical limit permits five extensions plus a payload. At the sixth
canonical index, a non-payload block was decoded into a spare header, but the
age/previous-node/hop-count/custody branches still wrote block data through
`ExtBlocks[CanonicalBlockIndex]`. That index is outside the five-element array.
Malformed wire input can reach this path before the enclosing decoder rejects
an invalid bundle. A spare header does not protect the block-data array.

Fix: reject a non-payload block at an index outside the extension array with
`BPLIB_CBOR_DEC_CANON_BLOCK_INDEX_ERR`, before writing any metadata. Remove the
misleading spare-header path. The final canonical slot still accepts payloads.

`cbor_bounds_regression` compiles the actual canonical decoder with QCBOR. It
checks rejection of excess previous-node, age, hop-count, custody, and unknown
blocks before any bundle metadata changes. It also checks the last valid age
extension, the payload slot, and the absolute canonical limit. CRC and unrelated
host/parser services are stubbed; this is not a full wire-ingress deployment test.

## 4. P2 — TCP transfers use the queue-poll timeout

Locations: `bpnode/fsw/src/bpnode_cla_in.c`, `bpnode_cla_out.c`, and
`bpnode/config/default_bpnode_mission_cfg.h`.

Fresh five-process validation passed the baseline but timed out recovering the
2→3 outage after node 2 restarted with the source stopped. Node 5 eventually
reconstructed the single segment but never published completion. The original
runtime and controller failure are retained under
`/tmp/bpsec-deployment-20261029/outage-2-3` and `outage-2-3.log`.

BPNode used `BPNODE_DATA_TIMEOUT_MSEC` (10 ms in the default 10 Hz configuration)
for TCP frame/ACK I/O as well as queue polling. The demo wakes peer tasks on a
200 ms timer; a healthy peer may not dispatch the frame and ACK within 10 ms.
Partial-transfer timeouts correctly close the stream, but this mismatch creates
repeated reconnects and stalls transfer/custody progress.

Fix: introduce mission-configurable `BPNODE_TCPCLA_IO_TIMEOUT_MSEC` (default
1000 ms) and use it for TCP send and receive. Queue polling retains its existing
budget. TCP deadlines remain finite and frame failures still close the stream.
Missions should size this budget for their scheduling and link latency; TCP I/O
can now span more than one task wakeup period.

The actual-ingress regression asserts that the TCP-specific timeout is passed
to the adapter. The TCP regression exercises a peer whose receive starts 60 ms
later, confirming that a finite TCP transfer budget permits delayed ACK dispatch.
Full deployment retry results are recorded in
[deployment validation](deployment-validation-2026-10-29.md).

## 5. P2 — Storage startup fails on transient reader locks and leaks error-path resources

Location: `bplib/bpa/stor/src/bplib_stor_sql.c`.

The lost-CCS deployment run stopped before sending any payload: node 1's native
cFS host remained alive after BPNode failed storage/cache initialization. The
old initializer had no SQLite busy handler and returned immediately if an
external reader briefly blocked switching the database to WAL mode. The old
logs did not preserve the underlying SQLite code for that particular run.
A deterministic regression reproduced storage initialization failure while a
read-only monitor held a short shared lock; releasing the reader 150 ms later
could not rescue the original initializer, which had already returned failure.

Fix: configure `sqlite3_busy_timeout` before initialization pragmas (default
1000 ms, overridable with `BPLIB_SQL_BUSY_TIMEOUT_MSEC`). Persistent contention
still fails within a bounded budget. Initialization errors print SQLite's code
and message, close the failed database connection, and clear its pointer.
Count/size queries used during initialization now finalize statements on failed
steps, so interrupted queries do not prevent connection cleanup.

`storage_init_regression` compiles the real storage SQL source and uses real
SQLite read locks. It covers a transient reader released after 150 ms, a
persistent reader with bounded failure and a cleared failed handle, and
interrupted count/size queries with no remaining prepared statements. The
regression failed against the original initializer and passes after the fix.

The deployment controller now waits for application readiness before monitoring
SQLite. `deployment_health_regression` also verifies that an alive cFS host with
a failed BPNode application is rejected promptly and that restart checks do not
reuse a readiness marker from the previous process. These checks distinguish
host-process health from application health; they do not retry or hide failures.

## 6. P1 — Successful rollback hides a failed write/COMMIT and falsely accepts custody

Location: `bplib/bpa/stor/src/bplib_stor_sql_store.c`, `BPLib_SQL_StoreImpl`.

The five-process storage-failure test injected an SQLite insert failure at
node 2. Its log recorded seven failed batches, yet node 5 published complete
output and node 1 released all custody. The failed runtime and logs are
preserved under `/tmp/bpsec-deployment-20261029/storage-failure-verified`.

For errors other than `SQLITE_FULL`, the old code replaced the failed
insert/COMMIT status with the result of `ROLLBACK`. A successful rollback
returned `SQLITE_OK`, so the caller treated the failed batch as committed,
accepted custody, and enqueued its memory copy for forwarding. This violates
durable custody: downstream success in that run does not make the acceptance
safe if the failed relay stops before forwarding.

Fix: preserve the original write/COMMIT error across rollback; clear the byte,
duplicate, and custody counts for the uncommitted batch. Output counts are also
cleared before preparation so an early failure cannot leave stale results.
Finalize/reset the insert statement pointers after each batch. The existing
storage finalizer now receives the error, refuses custody, frees the failed
batch, and does not forward it. Normal acceptance still follows successful
commit.

`storage_commit_regression` compiles the actual storage finalizer and SQL
sources, with real SQLite transactions and a two-bundle batch. A trigger fails
the second insert after the first insert succeeded; a separate deferred foreign
key violation fails at COMMIT. Both must leave zero rows and storage counters,
refuse both custody requests, free both bundles, and enqueue neither. The
success case then proves custody acceptance occurs after two rows are committed.
Custody signaling, queueing, time/configuration, and allocation boundaries are
observed/stubbed, while SQL and finalization behavior are real. Before the fix,
the regression caught a custody-accept call with an empty database. It passes
after the fix and under ASan/UBSan with leak detection enabled.

## Validation

A fresh configure/build before fixes succeeded in `/tmp/bpsec-review-20261029`.
All 12 original CTest entries passed with local socket access permitted. The
initial sandbox test run denied socket operations; those failures were not code
failures. Passing baseline tests did not cover the three bounds cases above.

Post-fix results:

- Configure/build in `/tmp/bpsec-review-20261029`: passed, including the new
  standalone decoder regression.
- `ctest --test-dir /tmp/bpsec-review-20261029 --output-on-failure --timeout 60`:
  all **13/13 tests passed** in 4.29 seconds with local sockets allowed.
- Fresh ASan/UBSan build of `memory_regression` and `cbor_bounds_regression` in
  `/tmp/bpsec-review-20261029-asan`: passed. Both tests passed with
  `ASAN_OPTIONS=detect_leaks=1:halt_on_error=1` and
  `UBSAN_OPTIONS=halt_on_error=1`, outside the sandbox for LeakSanitizer.
  No sanitizer error or leak was reported by those two targets. Other targets
  and staged dependency binaries were not rebuilt with sanitizers for this run.
- `python3 docs/check_documentation.py`: passed with 27 inventory entries,
  32 public Python classes/callables, and 34 relative links.

## Final deployment validation

The native Linux mission was rebuilt and the final BPNode/BPLib modules were
installed into isolated test runtimes. All **16/16 integration entries** and
**11/11 five-process deployment scenarios** passed after findings 4–6 were fixed.
Storage-initialization and failed-commit regressions also passed ASan/UBSan with
leak detection. The matrix covers baseline hashes/custody drain, three broken
hops with relay restart and source stopped, lost CCS, node 5 restart, wrong keys,
altered ciphertext, missing BCB, storage failure, and source IVs across restart.

The [deployment report](deployment-validation-2026-10-29.md) preserves the full
results, failed-run history, timings, exact commands, binary fingerprints,
keyless-relay checks, six-second custody stability checks, and limits. In
particular, the final storage-failure run retained all seven source custody
records, committed none at the failing relay, and published no output. The
source restart audit observed 20 distinct 96-bit IVs using the retained key.

## Compatibility and limits

Valid pool initialization, valid blob reads, and valid extension/payload layouts
retain their APIs. Invalid blob ranges and excess extensions now fail instead
of accessing unused or out-of-range memory. Callers must continue to keep bundle
metadata stable during access. Block writers retain their documented requirement
for valid decoded offsets and exactly one close after a successful open.

No existing recording, custody database, staged dependency library, key, or
runtime state was intentionally changed. Fresh deployment runtimes were created
for validation. Tests/builds use temporary output directories.
The original bounds-fix tests did not establish a complete deployment rerun.
Subsequent five-process results and remaining limits are recorded in the linked
deployment report. Native Windows, hardware power-loss durability, and an
exhaustive dependency leak audit remain outside this validation.
