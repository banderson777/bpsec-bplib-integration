### 1. P2 — Continuous transfer can succeed with entire segments missing

Location: `client-test/continuous_video_demo.py:81`, with EOF construction at
line 31. The completion check only rejects nonempty `pending`. A segment for
which every datagram was lost never enters that dictionary. Receiving complete
segment 1 followed by EOF therefore succeeds without segment 0. Receiving only
EOF also succeeds with no output. Missing trailing segments are undetectable
because EOF contains no expected segment count or manifest.

This is silent loss beyond the documented lack of retransmission. A viewer
waiting for contiguous filenames can wait forever after the sender exits
successfully. The assertion in `docs/code-guide.md` that both non-custody demos
fail incomplete transfers at EOF is consequently too broad.

Evidence: invoked the actual `ground()` with its socket replaced by a receiver
supplying real authenticated records from `Codec`, using a temporary output
directory. Both cases returned normally:

```text
missing segment zero RETURNED SUCCESS: ['ground-000001.ts']
all data lost RETURNED SUCCESS: []
```

Recommended change: authenticate an expected segment count or manifest in EOF,
then require exactly the expected completed segment IDs and no partial segments.
Specify empty-input/empty-segment behavior. Add regressions for missing initial,
middle, trailing, and all segments, plus a successful out-of-order complete run.
Update the documented EOF fields and completion contract with that change.

Status: fixed on 2026-10-07. EOF now carries an authenticated segment count;
ground checks the exact completed ID set and rejects pending parts. Empty
segments use one empty part. Three Python regression methods cover missing
initial/middle/trailing/all segments, partial segments, unexpected IDs, invalid
EOF counts, reordering, duplicates, and empty transfers/segments.

### 2. P2 — Interrupted polling can exceed the transport deadline

Location: `integration/bplib_tcp_cla.c:131-138`. `wait_fd()` repeats `poll()`
with the original relative timeout after every EINTR. Although `transfer()`
calculates the remaining deadline before entering this helper, it cannot
recheck the deadline until the helper returns. Repeated signals can therefore
extend a finite socket operation indefinitely and keep its I/O mutex occupied.
The same helper also serves connection/accept waits.

Evidence: a temporary C harness included the actual adapter source, polled an
empty pipe through `transfer()` with a 20 ms deadline, and delivered ten
SIGALRM signals at 10 ms intervals with a non-restarting handler:

```text
20ms transfer: elapsed=121 ms, signals=10, timeout=yes
```

The pipe exercises the same POSIX poll/EINTR path without needing network I/O;
the operation times out before any socket read. Timing includes normal scheduler
variation, but the repeated full timeout after interruption is explicit in code.
This contradicts the effective deadline guarantee described in the code guide
and the previous review's timeout fix; it is separate from the documented
unbounded mutex acquisition and DNS resolution.

Recommended change: recompute remaining time after each interrupted wait using
a monotonic absolute deadline, preserving zero as the public infinite-wait
option without turning an expired finite deadline into an infinite wait. Cover
repeated interruptions in a transport regression and check connect/accept too.

Status: fixed on 2026-10-07. Poll retries now recompute the remaining monotonic
deadline, clamp waits to `INT_MAX`, and preserve zero as infinite. The C
regression interrupts receive and accept with repeated signals and checks their
finite deadlines, idle socket preservation, listener cleanup, and a subsequent
zero-timeout receive. Connect uses the same corrected poll helper; a separate
interrupted-connect scenario was not exercised.
